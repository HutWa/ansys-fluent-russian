# Участие в проекте

## Основные правила

1. Переводьте только пользовательский текст, сохраняя идентификаторы, TUI-команды, API, пути и placeholders без изменений.
2. Перед новым вариантом проверьте `dictionary/glossary_ru.json`.
3. Не добавляйте бинарные файлы Ansys, лицензии, установщики, извлечённые оригинальные ресурсы или существенные фрагменты документации Ansys.
4. Размещайте переводы строго в каталоге версии: `translations/vYYYYRN/`.

## Новый термин

Добавьте предложение в Pull Request: английский термин, русский вариант, контекст Fluent, статус (`needs_review` или `reviewed`) и краткое обоснование. После согласования обновите глоссарий и `terms_reference.txt`.

## Проверка

Запустите:

```text
python scripts/validate_translation.py <путь-к-набору-переводов>
python scripts/check_repository.py
python -m unittest discover -s tests -v
```

В Pull Request укажите версию Fluent, формат ресурса, затронутые UI-модули и результаты проверки. GitHub Actions повторит эти проверки автоматически.

Лимит проекта — 20 MiB на файл, что строже технического лимита GitHub. Если небольшой собственный артефакт действительно должен превышать этот предел, сначала обсудите изменение правила; Git LFS нельзя использовать для обхода запрета на публикацию материалов Ansys.

## Неоднозначные строки

Используйте статус `needs_context`, сохраните исходную строку и укажите путь ресурса, раздел UI и возможные значения. Не угадывайте перевод слов `Cell`, `Zone`, `Monitor`, `Report`, `Solution`, `Patch`, `Surface` и `Field` вне контекста.

Для технически понятной строки после первого прохода используйте `translated`. Для спорного термина с известным контекстом используйте `needs_review` и перечислите рассматриваемые варианты. Статус `reviewed` назначается только отдельным проверочным проходом пользователя или назначенной модели, а не самим автором первичного перевода.
